# Прод и тестовый стенд

Одна кодовая база, два явных режима запуска. `tests/` остаётся в репозитории
для проверки изменений. Продуктивные задания запускаются через `prod`,
эксперименты и проверка изменений — через `staging`.

| Настройка | prod | staging |
|---|---|---|
| Файл секретов | `.env` | `.env.staging` |
| База сделок и планов | `trading.db` в корне (существующая) | `runtime/staging/trading.db` |
| Рабочий каталог | `runtime/prod/` | `runtime/staging/` |
| Отчёты и графики с относительными путями | внутри рабочего каталога | внутри рабочего каталога |
| Архив заданий Hermes | существующий пользовательский | `runtime/staging/cron/` |
| Тесты и бэктесты через запускатель | запрещены | разрешены |

Существующая рабочая база и настройки сохраняются. Стенд стартует с пустой базой,
которую создаёт первая команда журнала/планов. Скрипт health базу не создаёт.
Секреты, базы и каталоги `runtime/` исключены из Git.

## Подготовка

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
# Только если .env ещё отсутствует: скопировать .env.prod.example в .env.
# Для сетевых проверок стенда: скопировать .env.staging.example в .env.staging.
```

Заполните файлы самостоятельно. Не копируйте рабочий токен на стенд.
Запускатель стенда удаляет унаследованные `TINKOFF_*` и `MOEX_*`, выбирает
`.env.staging` и не загружает `.env`. В файлах выбранного режима учитываются
только `TINKOFF_*`: пути состояния задаёт запускатель.
Для брокерских запросов стенда нужен явно заданный `TINKOFF_ACCOUNT_ID`.

`staging` здесь означает изоляцию локального состояния, а не брокерскую песочницу:
при заданных реквизитах сетевые скрипты читают реальные рыночные данные и состояние
указанного счёта. Код не отправляет биржевые заявки. Для модульных тестов и
офлайн-бэктестов токен не требуется.

## Рабочие задания

Из корня проекта:

```sh
.venv/bin/python scripts/run_env.py prod morning-imoexf
.venv/bin/python scripts/run_env.py prod morning-usdrubf
.venv/bin/python scripts/run_env.py prod monitor
.venv/bin/python scripts/run_env.py prod evening
.venv/bin/python scripts/run_env.py prod health
.venv/bin/python scripts/run_env.py prod cli trade list
.venv/bin/python scripts/run_env.py prod agent get --ticker IMOEXF
```

## Проверка изменений

```sh
.venv/bin/python scripts/run_env.py staging test
.venv/bin/python scripts/run_env.py staging cli trade list
.venv/bin/python scripts/run_env.py staging morning-imoexf
.venv/bin/python scripts/run_env.py staging monitor
.venv/bin/python scripts/run_env.py staging backtest
```

Последние три команды используют сеть. Бэктест пишет данные и HTML в
`runtime/staging/reports/`. Для повторного запуска на сохранённых стендом данных:

```sh
.venv/bin/python scripts/run_env.py staging backtest --offline
```

Другие исследовательские задания: `execution-backtest`, `trend-backtest`,
`benchmark`, `walkforward`, `random-execution`. Параметры команды идут после её
имени. `cli` передаёт параметры в `python -m usdrubf`.

Все относительные пути аргументов, включая `agent submit --file`, разрешаются
от рабочего каталога режима. Для существующих файлов проекта указывайте
абсолютный путь. Явные `--db`, `--output`, `--data-dir` позволяют переопределить
назначение: не направляйте стенд на рабочие файлы. Это разделение настроек,
а не защита средствами ОС; код и пользователь имеют доступ к файловой системе.

## Перевод заданий и выпуск изменений

1. Проверить изменения командой `staging test` и нужными заданиями стенда.
2. Зафиксировать проверенную версию кода в Git.
3. В расписании использовать абсолютные пути к Python и `scripts/run_env.py`,
   затем `prod` и имя задания. Существующие расписания автоматически не меняются.
4. Сохранять резервную копию рабочей базы перед изменением схемы/обновлением.
   Для отката кода использовать предыдущий проверенный коммит; при изменении
   схемы также учитывать совместимость базы.

Старые прямые вызовы скриптов поддерживаются для совместимости. Изоляция
режимов гарантируется настройками нового запускателя; используйте его для
всех новых заданий. Разные ветки Git сами по себе базы и секреты не разделяют.
