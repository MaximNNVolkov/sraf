# Ретро-тест USDRUBF v0.1001

Актуальная спецификация после уточнений владельца. Исходный план
[RETROTEST_V0_0001_PLAN.md](RETROTEST_V0_0001_PLAN.md) остаётся историческим
описанием; эта версия реализует именно исследовательский цикл агента,
а не детерминированный baseline. Изменения правил входа, TP1 и разрешение
разработки/загрузки данных получены отдельно от исходного плана.

## Изоляция

Ветка: `research/usdrubf-retrotest-v0.1001`. Код: `research/retrotest/`.
Продуктивные `usdrubf/`, `scripts/`, `.env`, `trading.db`, расписание не меняются.
Существующие продовые функции расчёта признаков импортируются только для чтения.
Во время replay сетевые запросы отсутствуют. Сетевой доступ и загрузка рабочего
токена для чтения данных используются только явной командой `download`.

Данные и результаты находятся в игнорируемом Git каталоге `runtime/retrotest/`:

```text
raw/USDRUBF_<год>.zip                         # исходные минутные архивы
 datasets/USDRUBF_20220426_20260601/
   candles.sqlite                           # общая история всех таймфреймов
   manifest.json                            # диапазон, запросы, metadata, SHA-256
   quality.json                             # прогрев, сверка M1/M15, ограничения
 results/v0.1001/
   model.json                               # запрет менять модель под прежним номером
   samples/<hash>.json                       # выборка origins, seeds, популяция
   <run_id>/manifest.json                    # замороженные промпты/config/code hashes
   <run_id>/run.sqlite                       # часы, контексты, решения, сделки, audit
   <run_id>/results.json                     # экспорт текущих результатов
```

Каталоги в дереве показаны относительно `runtime/retrotest/`, без начальных пробелов.
Большая база и секреты не отправляются в GitHub. Для переноса базы на другую
машину копируется весь каталог dataset и проверяется командой `verify`.

## История

Подтверждённый период: **01.01.2023–01.06.2026 включительно**, по московским датам.
Ранняя история с 26.04.2022 сохраняется для прогрева. Свечи: M1, M15, M30,
H1, H4, D1, W1. OHLCV хранятся без искусственного заполнения пропусков.

Источники: [годовые минутные архивы T-Invest](https://developer.tbank.ru/invest/services/quotes/get_history)
и нативные exchange-свечи GetCandles. Для дат, где архив расходится с нативными
M15 по OHLCV, M1 повторно запрашивается через exchange GetCandles. Записываются
исходные и новые хеши, источник и даты; исходные ZIP остаются сохранены.
Остаточные расхождения сохраняются в quality.json, а не исправляются догадками.

SQLite имеет уникальный ключ `(timeframe, begin)` и проверки OHLCV. После загрузки
dataset запечатывается хешами. Replay открывает базу `mode=ro`, проверяя хеши.
Повторный download в запечатанный каталог запрещён; для обновления нужен новый.
Прерванная загрузка продолжается из `candles.building.sqlite` по журналу запросов.

Доступность свечи определяется как `begin + timeframe <= cutoff`;
для D1 — 24 часа, W1 — 7 дней. Это консервативная граница, которая не позволяет
подмешать незавершённую свечу. Исторический статус торгов неизвестен и явно
помечен, вместо подстановки сегодняшнего. Цена — close последней доступной M1,
её время — граница завершения M1, а не точный timestamp последней сделки.

Полнота относительно официального исторического календаря/halts пока не
сертифицирована. Текущие tick size/lot size записаны как metadata snapshot;
историческая серия изменения спецификаций не загружена. Фандинг, комиссии,
ликвидность и дополнительное проскальзывание не моделируются. До выводов об
эффективности стратегии эти ограничения нужно отдельно закрыть.

## Часы и контракт агента

1. `create --origin YYYY-MM-DD` создаёт отдельный прогон на 08:00 МСК.
   Дата должна иметь наблюдаемые торги и минимум 250 завершённых D1 до origin.
   Ранние даты без нужного прогрева отклоняются с объяснением.
2. `context` выдаёт факты в продовой структуре W1/D1/H4/H1, исторические
   свечи, состояние и уникальный `context_id`. Все свечи завершены к cutoff.
3. Агент отправляет одну из команд: `PLAN`, `NO_TRADE`, `WAIT`, `CANCEL`,
   `CONFIRM_ENTRY`. Любое решение содержит актуальный `context_id` и `reason`.
   Контекст можно использовать для решения только один раз.
4. `PLAN` содержит `direction: LONG|SHORT`, `entry` как исходный ориентир,
   `stop`, `tp1`, `tp2`, текст `entry_condition` и анализ. Бэк проверяет порядок
   и шаг уровней, но не выбирает сценарий за агента. TP2 строго дальше TP1.
5. `NO_TRADE` содержит причину и условие пересмотра в `entry_condition`.
6. `advance` разрешён после решения агента. Он переводит часы
   `08 → 10 → 12 → 14 → 16 → 18 → 20 → следующее наблюдаемое утро 08`.
   Новые H1 передаются в `new_h1_candles`; при обычном шаге это до двух баров,
   при переходе через ночь их может быть больше. Текущие планы сохраняются.
7. Агент сам подтверждает выполнение своего ранее описанного условия через
   `CONFIRM_ENTRY`: `evidence` — список `{begin, reason}` по видимым завершённым
   свечам. Бэк проверяет видимость ссылок, но не истинность текстового анализа.
   Подтверждение разрешено только на мониторинге после 08:00 и при сохранённом
   плане. До фактического входа и до CONFIRM_ENTRY сохраняется возможность
   обновить/отменить план новым решением.
8. CONFIRM_ENTRY в T планирует вход в T+15 минут по close M15 `[T,T+15)`.
   Цена и будущая свеча не раскрываются до advance. Если такой свечи нет,
   вход отменяется `CANCEL_ENTRY_NO_BAR`. Если фактическая цена оказалась
   за stop/TP1, — `CANCEL_ENTRY_INVALID_LEVELS`. При конфликте источников
   — `CANCEL_ENTRY_DATA_CONFLICT`. Уровни не подгоняются к новой цене.
9. После подтверждения и открытия позиции разрешён только `WAIT`: уровни
   заморожены, исполнение ведёт бэк. Новая сделка возможна после закрытия
   прежней и нового решения агента на очередном мониторинге.

Полные prompts/response, модель и параметры вызова можно сохранять в `metadata`
JSON решения. Версия содержит копии текущих продовых промптов и специальный
replay.md, заменяющий реальные команды историческими. Для независимых origins
следует использовать отдельные контексты модели; backend сам LLM не вызывает.

## Исполнение и результаты

- Экстремумы до фактического entry не учитываются. После входа бэк проверяет
  каждую M1 последовательно во всех сессиях, включая часы между мониторингами.
- Stop/TP срабатывают по high/low, а не только по close. Stop при гэпе
  исполняется по open; цели консервативно по своему уровню.
- TP1 закрывает 50%, стоп остатка сразу переносится на фактический entry.
  Остаток закрывается по TP2 или новому stop. Записывается каждый частичный выход.
- При однозначном касании внутри M1 время хранится как интервал
  `time_from..time_to` с точностью `within_1m_bar`. Точная секунда неизвестна.
  Для исполнения на open время задаётся как `bar_open`.
- Если M1 касается stop и цели, либо порядок TP1/нового stop внутри M1 неясен,
  исход `AMBIGUOUS`, без выдуманного P/L. Конфликт данных даёт `DATA_CONFLICT`.
  В обоих случаях прогон становится `UNRESOLVED` и новые сделки запрещены.
- В конце истории открытая позиция получает `OPEN_AT_DATA_END`, без фиктивного
  закрытия и полного P/L. Подтверждённый вход за концом истории также отмечается.
- Для закрытой позиции сохраняются фактические entry, время, stop, обе цели,
  цены/доли/временные интервалы выходов, последняя и взвешенная цена закрытия,
  `WIN|LOSS|BREAKEVEN`, gross % и R. Итоговый процент взвешен по долям позиции.
  После TP1 и stop в безубытке остатка итог может оставаться выигрышем.
- Проценты относятся к цене позиции, не к депозиту. Net отсутствует (`null`).
  Неоднозначные/незавершённые случаи не превращаются в выигрыши или проигрыши.
- `finish` окончательно завершает прогон, обрабатывая оставшуюся историю для
  существующей позиции/подтверждения. Это явное раскрытие будущего: продолжать
  решения агента в этом прогоне после finish нельзя.

Журнал событий связан SHA-256 цепочкой, состояние связано с последним audit
хешем. Манифест содержит снимки версии модели и хеши используемого кода.
При изменении кода старый прогон нельзя продолжить: нужно восстановить код
или создать новый прогон. Служебные timestamps/UUID не делают вызовы LLM
детерминированными; сохранённые решения позволяют аудит фактического прогона.

## Команды

Запускать из корня репозитория:

```sh
.venv/bin/python -m research.retrotest download
.venv/bin/python -m research.retrotest verify
.venv/bin/python -m research.retrotest sample --seed 1001 --audit-seed 2001 --count 100
.venv/bin/python -m research.retrotest create --origin 2025-06-02 --version v0.1001
.venv/bin/python -m research.retrotest context --run /absolute/path/to/run
.venv/bin/python -m research.retrotest submit --run /absolute/path/to/run --file decision.json
.venv/bin/python -m research.retrotest advance --run /absolute/path/to/run
.venv/bin/python -m research.retrotest results --run /absolute/path/to/run
.venv/bin/python -m research.retrotest finish --run /absolute/path/to/run
.venv/bin/python -m research.retrotest serve --port 8765
```

HTTP слушает только `127.0.0.1`. Маршруты:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Проверка сервиса |
| POST | `/runs` | JSON `origin`, `version`, необязательные `dataset`, `metadata` |
| GET | `/runs/<version>/<run_id>/context` | Контекст до текущего cutoff |
| POST | `/runs/<version>/<run_id>/decision` | JSON решения агента |
| POST | `/runs/<version>/<run_id>/advance` | Следующий мониторинг |
| GET | `/runs/<version>/<run_id>/results` | Наблюдаемые результаты |
| POST | `/runs/<version>/<run_id>/finish` | Завершить прогон и раскрыть исход |

Загрузка истории через HTTP недоступна. Ошибки условий возвращаются JSON с
HTTP 400, неверный метод — 405, неизвестный прогон — 404.

## Версии

```sh
.venv/bin/python -m research.retrotest bump --from-version v0.1001
# Создаётся v0.1002, редактируем её промпты/правила модели до первого прогона.
```

Каждый тюнинг получает следующий номер: v0.1001 → v0.1002 → v0.1003.
Предыдущая версия не перезаписывается. После первого прогона её model hash
фиксируется в `results/<version>/model.json`; изменение под тем же номером
запрещается. Параметры исполнения этой реализации фиксированы правилами владельца
(15 минут, 50% TP1, перенос stop); изменение этих параметров требует также
изменения движка, одних правок config недостаточно.

## Проверки

```sh
.venv/bin/python -m unittest discover -s tests/retrotest
.venv/bin/python scripts/run_env.py staging test
```

Проверяются отсутствие будущих свечей, часы/одноразовый context_id, подтверждение
агентом, лаг, отмена невалидного входа, отсутствие исполнения до entry, оба
направления, TP1/перенос stop, гэпы, M1 ambiguity, несовпадение источников,
незавершённые исходы, хеши/audit и увеличение номера версии.
