# Обратная связь Hermes → бэкенд

Агент выбирает торговую идею. Бэкенд собирает факты, проверяет формальные
ограничения, сохраняет решение и проверяет его срабатывание. Никаких биржевых
поручений этот протокол не отправляет.

## Последовательность

1. Утренний скрипт получает T-Invest W1/D1/H4/H1 и состояние брокера. Решение
   строится по режиму W1, направлению D1 и подтверждению H4; H1 передаётся только
   для технической проверки пробоя/ретеста. В SQLite
   сохраняется неизменяемый снимок `analysis_contexts`. Ответ содержит
   `agent_handoff.context_id` и задачу `CREATE_PLAN` либо `KEEP_PLAN`.
2. Агент читает recent_candles (до 80 завершённых свечей каждого ТФ), последние
   40 подтверждённых экстремумов, уровни, индикаторы и волновые кандидаты.
   Индикаторы/экстремумы рассчитаны на всей запрошенной истории, не только на хвосте.
   Для сравнения между днями передаются previous_context и previous_agent_analysis.
3. Агент сам выбирает направление и цены либо объясняет NO_TRADE. До обратной
   связи состояние AWAITING_AGENT; оно не означает торгового решения «нет сделки».
4. Агент передаёт структурированный JSON через локальную CLI-команду `submit`.
5. Бэкенд возвращает ACCEPTED, REJECTED с errors либо REVIEWED для KEEP_PLAN.
   Отсутствие ответа/ошибка процесса не означает, что план сохранён.
6. Агент вызывает `get` и использует прочитанные уровни в окончательном отчёте.
7. Контроль в 12:01, 16:01 и 20:01 МСК проверяет сохранённый план без нового выбора
   направления; backend при этом не пропускает закрытые H1 технического replay.

## Команды

Из `/home/user1/moex`:

```sh
.venv/bin/python scripts/moex_agent_plan.py submit --file /tmp/agent-plan.json
.venv/bin/python scripts/moex_agent_plan.py get --ticker IMOEXF
```

Вместо файла можно указать `--file -` и передать JSON через stdin. При heredoc
заключай разделитель в одинарные кавычки, чтобы обоснование не выполнялось shell.

Для тестов задаётся `MOEX_TRADING_DB` или `--db PATH` **перед** submit/get. В обычном
задании использовать основной журнал. Не меняй базу напрямую и не создавай
новую базу в обход отказа валидатора.

Пример формы (числа условные, это не торговая рекомендация):

```json
{
  "context_id": "идентификатор из agent_handoff",
  "ticker": "IMOEXF",
  "decision": "LONG_SETUP",
  "reason": "Обоснование выбранной идеи по структуре рынка",
  "confidence": "medium",
  "analysis": {
    "w1": "Старший контекст и ограничения",
    "d1": "Направление, волатильность и горизонт",
    "h4": "Структура и происхождение выбранных уровней",
    "h1": "Точный пробой/ретест либо: не используется; решение по W1/D1/H4",
    "invalidation": "Какие факты отменяют идею"
  },
  "setup_type": "breakout",
  "entry": 100,
  "stop": 95,
  "tp1": 105,
  "tp2": 115
}
```

`structural_invalidation` — необязательная цена структурной отмены, на защитной
стороне входа. Для `NO_TRADE` и `KEEP_PLAN` поля цен и setup_type не нужны.
`NO_TRADE` — собственное решение агента, а не автоматическая замена отклонённого
черновика. `KEEP_PLAN` сохраняет новую оценку, но не меняет исходные уровни.

## Проверки бэкенда

- Нужны анализ режима W1, направления D1, подтверждения H4, ограниченной роли H1,
  отмены, обоснование, confidence и известные поля.
- Тикер должен совпадать с сохранённым снимком. Контекст принимается только
  в день его формирования, в течение 60 минут. Новый утренний сбор заменяет старый
  контекст. Просроченный снимок требует повторного утреннего сбора, не смены id в JSON.
- Цены конечны, положительны и кратны шагу инструмента. Для LONG:
  stop < entry < tp1 < tp2; для SHORT — обратный порядок. R/R до TP2 >= 2.
- Перед новым направленным планом CLI повторно проверяет реальные позиции,
  активные обычные заявки, последнюю биржевую цену и статус торгов.
- Существующая позиция/заявка запрещает новый вход. Зафиксированный агентом
  план в течение дня и активный многодневный сценарий не перезаписываются. Исключение:
  отменённый до активации сценарий может быть заменён по свежему контексту монитора;
  новый план также проходит полную проверку брокера и рынка. Допускается ровно
  один replacement исходного сценария за его торговый день.
- Replacement не перезаписывает исходную запись: он получает новый `plan_id`,
  `revision=1`, ссылку на исходный `root_plan_id` и отдельную последовательность
  `plan_events`. События revision 0 и revision 1 не объединяются.
- Наклон MA, выбор стороны, конкретные уровни и расстояние в ATR — решения
  агента, не скрытый алгоритмический отбор бэкенда.
- Повтор той же принятой заявки возвращает исходную квитанцию idempotent=true.
  После неё `get` показывает текущее состояние, которое мог изменить монитор.
- Ошибки не превращаются молча в NO_TRADE. Черновики и квитанции сохраняются
  в agent_feedback; автор, анализ, confidence и context_id — в принятом плане.

`ACCEPTED` подтверждает сохранение и формальную проверку. Процентный риск,
размер позиции, комиссии, проскальзывание и платежи вечного фьючерса пока не
проверяются полностью: в квитанции sizing_status=NOT_CALCULATED и
ruble_risk_verified=false. Не представляй такую квитанцию как разрешение
автоматически торговать. Расчёт объёма — отдельная задача.

План начинает действовать с момента приёма, а не со времени снимка или анализа.
Час, начавшийся до приёма, не используется для входа. Подтверждение и ретест
должны произойти после сохранения. За исполнением реальных поручений этот
протокол не следит как за собственными сделками — их состояние берётся у брокера.

## Единые правила отмены и стопа

Агент обязан использовать эти правила в `analysis.invalidation` и отчёте;
текст анализа не изменяет алгоритм мониторинга.

- При подготовке LONG стоп должен быть ниже entry и актуальной price из контекста;
  для SHORT — выше обеих цен. Аналогичную сверку с price агент выполняет для
  structural_invalidation, если она задана. При нарушении — NO_TRADE без
  искусственного переноса уровня. Это обязанность агента: ACCEPTED само по себе
  не доказывает выполнение этой сверки.
- До активации, в WAITING/CROSSED/HOURLY_CONFIRMED, касание stop отменяет план
  (CANCELLED). Это отмена ожидающей идеи, а не стоп-лосс исполненной сделки.
- После активации, в ACTIVE/TP1, касание stop означает STOPPED рыночного сценария;
  факт выхода и цену исполнения подтверждают только данные брокера.
- Касание проверяется по low <= stop для LONG и high >= stop для SHORT на
  завершённом часовом баре, начавшемся не раньше принятия плана. Закрытие за
  стопом не требуется. Проверка стопа предшествует подтверждению и ретесту:
  если час ретеста коснулся стопа, активации нет. Экстремумы часа успешной
  активации не засчитываются как последующее достижение целей.
- structural_invalidation хранится как поясняющий уровень; отдельного
  автоматического условия отмены по нему сейчас нет. Агент не должен обещать
  отмену по этому полю или подменять stop произвольным текстовым условием.
- Формулировка агента: «До входа касание stop отменяет ожидающий сценарий;
  после активации это стоп рыночного сценария. Проверка — по экстремумам
  завершённых часов, исполнение сделки проверяется у брокера».

Пример: при price=2503, entry=2523.5 и stop=2506 геометрия будущей LONG-сделки
верна, но сценарий не соответствует действующей отмене до входа. Агент должен
отправить NO_TRADE; нельзя обещать, что стоп начнёт учитываться только после входа.

## Установка в Hermes

Промпт утренних заданий: `prompts/moex_morning.md`. Он разрешает необходимые
локальные вызовы terminal и требует submit → get перед публикацией. Нельзя
оставлять старую инструкцию «Дополнительные инструменты не вызывай» для утра.
Требуется доступ к terminal; при его отсутствии агент обязан сообщить, что
план не сохранён. Само расписание и адрес доставки остаются прежними.
При ошибке/лимите модели контекст остаётся PENDING до `submit_before`. Если созданный
монитором replacement-контекст просрочен, следующий монитор помечает его `EXPIRED`
и создаёт новый свежий контекст для той же единственной допустимой replacement-версии.
Он не зависает в `AWAITING_AGENT`, не выбирает вход сам и не создаёт контекст при
позиции или обычной активной заявке. После принятия revision 1 новых replacements
этого исходного сценария в тот же торговый день нет; отменённое состояние сохраняется.
