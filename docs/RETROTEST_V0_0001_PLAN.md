# План ретро-тестирования USDRUBF v0.0001

## 1. Статус документа и блокирующий вопрос

> **ТРЕБУЕТСЯ ОТВЕТ ВЛАДЕЛЬЦА:** исторический диапазон указан буквально как
> `01.01.2023`—`01.06.206`. Конечная дата `01.06.206` выглядит неполной, но в
> этом плане она намеренно не исправляется и не трактуется как `01.06.2026`.
> До явного подтверждения конечной даты блокируются все количественные расчёты,
> построение множества eligible origins и выборка 100 точек.

Документ описывает будущую разработку отдельного приложения для ретро-тестирования
стратегии USDRUBF `v0.0001`. Он является планом, а не результатом теста и не
разрешает начинать загрузку данных или исполнять стратегию.

## 2. Цель и границы

### Цель

Спроектировать проверяемый протокол, который для 100 случайно выбранных точек
`origin` принимает решение только на доступных к каждой точке данных, а затем
оценивает фактическое развитие сценария по будущим H1-барам. Решение стратегии:

- `NO_TRADE`;
- `LONG`;
- `SHORT`.

Тест должен сохранять полный аудиторский след, отделять качество решения от
модели исполнения и явно показывать неоднозначные и незавершённые исходы.

### Не входит в эту задачу

- реализация приложения, движков, валидаторов, тестов, моков или заглушек;
- скачивание или генерация рыночных данных;
- запросы к T-Invest, MOEX, broker API или иным внешним источникам;
- запуск cron и изменение его конфигурации;
- изменение торгового или брокерского кода;
- изменение существующих отчётов, scripts, базы `trading.db`, `.env` или
  `OPEN_POSITIONS.md`;
- выполнение ретро-теста и публикация его результатов;
- push ветки и создание PR.

## 3. Версионирование и Git workflow

- Базовая версия стратегии и протокола: `v0.0001`.
- Следующие небольшие итерации: `v0.0002`, `v0.0003` и далее.
- Обозначение `v0.2` зарезервировано для зрелого этапа готовности к нормальным
  тестам и проверке на реальных деньгах; оно не является ближайшей версией.
- Любое изменение правил решения, уровней, исполнения, обработки TP1,
  комиссий, slippage, признаков или выборки требует новой версии конфигурации и
  сохранения её хеша.
- Все материалы стратегии, тестов и промптов хранятся только в репозитории
  `moex`.

Предусмотренный workflow:

1. От исходной ветки `moex-deploy` создать feature-ветку
   `research/usdrubf-retrotest-v0.0001`.
2. Подготовить план и в будущих задачах вести реализацию только в этой ветке или
   в согласованных последующих ветках.
3. Открыть PR после реализации соответствующего этапа.
4. Выполнить автоматические тесты, ручной аудит и review.
5. Merge разрешён только после прохождения критериев приёмки.

В рамках текущей задачи push и PR не выполняются.

## 4. Режимы принятия решения

### 4.1. Воспроизводимый baseline v0.0001

Доказательная метрика строится только на детерминированном decision/level engine:
одинаковые immutable dataset, origin, версия кода, конфигурация и seed должны
давать одинаковые решение и уровни. Baseline реализует текущие правила стратегии
через versioned strategy adapter. Нельзя подменять текущую модель упрощённой
SMA-моделью.

### 4.2. Research replay LLM

LLM replay — отдельный исследовательский режим, маркируемый как
`non-deterministic`; он не используется для доказательной метрики baseline.
Называть такой прогон воспроизводимым можно только при сохранении точного
historical context, полного prompt, полного response, model identifier/version,
параметров вызова, конфигурации и связанных хешей. Без исторических snapshots
точный replay невозможен, и результат нельзя выдавать за исходное решение
модели.

## 5. Архитектура будущего отдельного приложения

Приложение должно быть отделено от рабочих отчётов и торгового контура.

1. **Ingestion** — принимает предоставленные backend наборы, не изменяя
   оригиналы; проверяет формат и передаёт их валидатору.
2. **Immutable dataset manifest** — фиксирует происхождение, схему, диапазон,
   число строк и SHA-256 каждого файла. После запуска теста dataset не меняется.
3. **Origin sampler** — строит eligible population и равномерно выбирает 100
   уникальных origins по master seed.
4. **Feature assembler** — собирает признаки строго с timestamp не позднее
   source cutoff и сохраняет полный feature snapshot.
5. **Strategy adapter** — versioned-интерфейс текущей стратегии; выдаёт
   `NO_TRADE`, `LONG` или `SHORT`, reason и, для сделки, уровни.
6. **Entry tracker** — после origin ищет первое фактическое касание entry и
   обрабатывает только заранее описанные отмены до входа.
7. **Barrier/outcome engine** — после entry последовательно обрабатывает H1-бары,
   барьеры stop/TP1/TP2, неоднозначность и конец данных.
8. **Metrics/reporting** — считает допустимые агрегаты отдельно для gross, net,
   resolved, unresolved и `NO_TRADE`.
9. **Audit store** — append-only хранилище входов, решений, переходов состояний,
   хешей и объяснений; позволяет восстановить каждую строку отчёта.

Границы модулей должны исключать доступ strategy adapter и feature assembler к
будущим данным. Outcome engine не имеет права пересчитывать исходное решение.

## 6. Контракт решения на origin

Для каждого origin сохраняются:

- уникальный `run_id`, `case_id`, origin timestamp в UTC и MSK;
- версия стратегии, версия схемы и master seed;
- `source_cutoff` — максимальный timestamp данных, доступный решению;
- решение и полный `reason`;
- полный feature snapshot с timestamp источников;
- SHA-256 prompt, config, code revision и dataset manifest;
- для LLM replay дополнительно model identifier/version, параметры, historical
  context, prompt и response;
- для `LONG`/`SHORT`: точные `entry`, `stop`, `TP1`, `TP2`, направление и
  versioned правила после TP1;
- для `NO_TRADE`: только причины и заранее определённые условия
  пересмотра/разрешения входа — без выдуманных entry, stop, TP и P&L.

Уровни должны быть валидны относительно tick size. Для `LONG` ожидается
`stop < entry < TP1 <= TP2`, для `SHORT` — `TP2 <= TP1 < entry < stop`, если
versioned стратегия явно не задаёт иной, отдельно проверяемый контракт.

## 7. Конечные автоматы и статусы

### 7.1. Торговый сценарий

1. Решение `LONG`/`SHORT` переводит сценарий в `PENDING_ENTRY`.
2. Начиная строго после origin, entry tracker читает H1-бары по времени и ищет
   первое касание фактической цены entry. До касания entry исполнение и P&L не
   моделируются.
3. Если до entry сработало заранее versioned условие отмены, статус становится
   `CANCELLED_BEFORE_ENTRY`. Произвольная отмена задним числом запрещена.
4. Первое касание entry переводит сценарий в `ACTIVE`; сохраняются timestamp и
   фактическая цена входа по правилам исполнения.
5. После entry H1-бары отслеживаются без произвольного временного горизонта до
   stop, `TP1` или `TP2` либо до конца доступного набора.
6. Касание TP1 фиксирует `TP1`. Дальнейшая доходность допустима только при
   заранее заданной, versioned политике: например, доля частичной фиксации,
   перенос stop и правила остатка позиции. Без неё `TP1` остаётся отдельным
   outcome, а итоговая доходность после TP1 не рассчитывается.
7. Касание TP2 даёт `TP2`; касание stop — `STOPPED`.
8. Если один H1-бар одновременно касается применимых stop и TP, результат —
   `STOP_FIRST_AMBIGUOUS` (представление правила `STOP_FIRST/ambiguous`).
   Внутрибарный порядок не изобретается. Базовый баровый режим консервативно
   применяет stop первым для классификации, но не выдаёт неоднозначный результат
   за точно наблюдавшийся порядок.
9. Если сценарий не завершён на последнем доступном баре, он получает
   `OPEN_AT_DATA_END`; это не stop и не TP и показывается отдельно.

Optional-режим с историческими bid/ask/ticks может разрешать внутрибарный порядок
и моделировать исполнение точнее, но его результаты маркируются отдельно и не
заменяют базовый консервативный H1-режим.

### 7.2. NO_TRADE

1. Исходное решение имеет статус `NO_TRADE` и не содержит торговых уровней или
   P&L.
2. Если до конца применимого наблюдения режим отменился, не активировав заранее
   заданное условие пересмотра, outcome — `NO_TRADE_VALID`.
3. При наступлении условия пересмотра outcome — `REVIEW_TRIGGERED`; требуется
   новое независимое решение на новом cutoff. Оно не превращается автоматически
   в сделку исходного сценария.
4. Отдельная аналитика missed move допустима лишь по заранее утверждённой
   формуле и никогда не называется доходностью.

Обязательный словарь статусов: `NO_TRADE`, `PENDING_ENTRY`,
`CANCELLED_BEFORE_ENTRY`, `ACTIVE`, `TP1`, `TP2`, `STOPPED`,
`STOP_FIRST_AMBIGUOUS`, `OPEN_AT_DATA_END`, `REVIEW_TRIGGERED`,
`NO_TRADE_VALID`.

## 8. Формулы доходности и риска

Обозначения: `E` — фактическая цена entry, `X` — фактическая цена выхода,
`S` — исходный stop, `q` — знаковое направление (`+1` для LONG, `-1` для
SHORT), `C` — суммарные комиссии в процентах от базы позиции, `L` — суммарный
slippage в процентах. Все величины и стороны начисления фиксируются в
конфигурации запуска.

### LONG

- gross, %: `100 × (X - E) / E`;
- net, %: `gross% - C - L`;
- исходный риск, %: `100 × (E - S) / E`;
- `R = gross% / risk% = (X - E) / (E - S)`.

### SHORT

- gross, %: `100 × (E - X) / E`;
- net, %: `gross% - C - L`;
- исходный риск, %: `100 × (S - E) / E`;
- `R = gross% / risk% = (E - X) / (S - E)`.

Эквивалентная общая gross-формула: `100 × q × (X - E) / E`. При прибыльном
short (`X < E`) знак положительный, при убыточном (`X > E`) — отрицательный.
Gross и net никогда не смешиваются и агрегируются в отдельных колонках.

Комиссии и slippage — обязательная versioned конфигурация без значений по
умолчанию. Конфигурация определяет единицы, ставку и базу каждой комиссии,
стороны начисления, модель slippage для entry/exit/частичных выходов, округление
к tick size и применение к LONG/SHORT. Если параметры не заданы, net-метрики не
считаются. Для частичной фиксации итоговые gross/net/R являются
взвешенными по фактически закрытым долям; незакрытый остаток не получает
фиктивную цену выхода.

Дополнительно сохраняются длительность `origin → entry`, `entry → outcome` и
`origin → outcome` в часах и числе H1-баров.

## 9. Контракт данных от backend

Все обязательные поля должны иметь документированные тип, nullable-policy и
единицы. Каноническое время — UTC; MSK (`Europe/Moscow`) предоставляется как
явное отображение, а не как замена UTC. Timestamp должны быть ISO 8601 с offset
либо целым Unix time с зафиксированной единицей.

| Набор/поле | Обязательность | Формат и правила полноты |
|---|---|---|
| OHLCV W1/D1/H4/H1 USDRUBF | Required | Не менее 3 лет подтверждённого диапазона плюс warm-up не менее 250 D1 торговых сессий до первого eligible origin. Числовые OHLCV, `begin`, `end`, `completed`; OHLC непротиворечивы, объём неотрицателен, ключ `(instrument, timeframe, begin)` уникален. Незавершённые свечи не используются как завершённые. |
| Timestamp | Required | `begin` и `end` в UTC и соответствующее представление MSK; однозначные границы интервала, сортировка и отсутствие дублей. Правила включения границ документированы. |
| Instrument metadata | Required | Идентификатор USDRUBF, board, tick size, lot size, валюта/единица цены и период действия metadata. Изменения во времени версионируются. |
| Торговый календарь | Required | Сессии, выходные, праздники, укороченные дни, клиринги; исторические статусы торгов и halts с begin/end и причиной, если доступна. Пропуск бара отличим от отсутствия торгов. |
| Непрерывный/вечный фьючерс | Required | Точный идентификатор серии, правила построения/ролловера, даты и коэффициенты склейки, источник, а также явно перечисленные отсутствующие периоды. Запрещена скрытая back-adjustment. |
| Volume, open interest, settlement | Conditional required | Обязательны, если хотя бы одно поле использует текущая стратегия; единицы, момент публикации и политика missing values фиксируются. Нельзя восстанавливать будущими значениями. |
| Historical bid/ask/last | Optional для baseline | Timestamp UTC, цена, размер, venue/board и качество. Используется только улучшенным режимом исполнения. |
| Ticks | Optional для baseline | Timestamp UTC с достаточной точностью, тип/сторона события, price, size и sequence id. Нужны для разрешения внутрибарного порядка, если реально доступны и полны. |
| Dataset manifest | Required | Для каждого CSV/Parquet: source URL и параметры, extraction time UTC, schema version, SHA-256, rows, min/max timestamps, размер и идентификатор набора. Manifest также имеет собственный SHA-256. |
| Historical decision snapshots | Required только для точного LLM replay | Полные historical context, prompt, config, model identifier/version, параметры и response. Для детерминированного baseline не требуются. |

### Критерии приёмки данных

- manifest и SHA-256 проходят проверку, число строк и min/max совпадают с
  фактическими файлами;
- схема, типы, timezone, единицы, nullable-policy и уникальные ключи валидны;
- свечи отсортированы, не дублируются, OHLC-ограничения соблюдены;
- полнота проверяется относительно торгового календаря; каждый gap
  классифицирован как отсутствие торгов, halt или дефект данных;
- H1 полностью покрывает будущее каждого eligible origin до barrier outcome или
  до документированного конца dataset; конец данных не маскируется;
- D1 warm-up содержит не менее 250 завершённых сессий, а каждый индикатор имеет
  требуемую историю на своём timeframe;
- roll/continuous series можно однозначно восстановить по правилам и metadata;
- данные, опубликованные после origin, не попадают в feature snapshot даже если
  относятся к более раннему периоду;
- обязательные conditional поля присутствуют, если их запрашивает стратегия;
- optional bid/ask/ticks не повышаются до required для базового барового теста,
  а их отсутствие явно отражается в capabilities manifest.

## 10. Протокол 100 тестов

1. После подтверждения конечной даты зафиксировать immutable dataset и manifest.
2. Зафиксировать версию стратегии, code revision, config, master seed и алгоритм
   PRNG/его версию.
3. Построить множество eligible origins без просмотра их будущей доходности.
   Origin должен иметь достаточно данных до source cutoff для максимального
   lookback каждого индикатора, включая минимум 250 D1 сессий warm-up.
4. Требование будущей полноты применяется только к технической наблюдаемости:
   должны присутствовать полные H1-данные от origin до всех наблюдаемых
   barrier outcomes либо до явно зафиксированного конца доступного dataset.
   Сценарии на конце не исключаются из-за незавершённого результата, а получают
   `OPEN_AT_DATA_END`. Запрещена фильтрация по знаку, размеру или удобству
   будущей доходности.
5. Равномерно, без возвращения выбрать ровно 100 уникальных origins из полного
   eligible population фиксированным master seed. Сохранить population size,
   отсортированный список кандидатов, алгоритм выборки и выбранные origins.
6. Для каждого origin собрать признаки только из данных с publication/availability
   timestamp не позже source cutoff. Нормализация, индикаторы, settlement,
   ролловеры и старшие timeframe не могут использовать незавершённый будущий бар.
7. Запустить детерминированный strategy adapter и заморозить решение, уровни,
   reason, snapshot и хеши до чтения outcome engine будущих H1-данных.
8. Обработать entry и barrier outcomes конечными автоматами из раздела 7.
9. Повторный запуск на тех же артефактах обязан побитно воспроизводить baseline
   decisions и структурированные outcomes (кроме заранее исключённых служебных
   timestamp запуска).
10. Вручную проверить 10 строк, выбранных до просмотра результатов отдельным
    фиксированным audit seed: cutoff и отсутствие leakage, исходные свечи,
    признаки, решение/уровни, первое касание entry, последовательность барьеров,
    формулы gross/net/R, комиссии/slippage и финальный статус. Ошибки и решения
    review сохраняются в audit log, строки не подменяются удобными примерами.

## 11. Метрики и отчётность

Отчёт показывает как минимум:

- counts и доли всех решений и конечных статусов;
- coverage: eligible population, выбранные 100, отклонённые origins по каждой
  технической причине;
- win rate только для чётко определённого набора resolved trades и с явным
  знаменателем;
- distributions gross %, net % и R: count, mean, median, standard deviation,
  min/max и согласованные quantiles;
- expectancy отдельно в gross %, net % и R с доверительным интервалом или
  bootstrap-описанием методики;
- суммарные gross и net результаты только при заранее определённых правилах
  агрегации позиции; последовательное compounding не предполагается без модели
  капитала;
- длительности до entry и от entry до закрытия, долю pending/cancelled;
- `STOP_FIRST_AMBIGUOUS` и `OPEN_AT_DATA_END` как отдельные unresolved группы;
- TP1 отдельно: доля касаний и доходность только при утверждённой политике после
  TP1;
- для `NO_TRADE`: `NO_TRADE_VALID`, `REVIEW_TRIGGERED`, время до review и
  заранее определённую missed-move аналитику, которая не смешивается с P&L;
- сравнение baseline и LLM research replay только как исследовательский срез,
  без включения LLM replay в доказательные метрики.

Для `STOP_FIRST_AMBIGUOUS` нельзя считать точные exit price, gross %, net %, R,
win/loss, expectancy и длительность до фактического закрытия: H1 не определяет
внутрибарный порядок. Их можно показать отдельными консервативными bounds или
сценарной оценкой, явно не смешивая с observed metrics. Для
`OPEN_AT_DATA_END`, `PENDING_ENTRY`, `CANCELLED_BEFORE_ENTRY`, `NO_TRADE` и
`REVIEW_TRIGGERED` торговая доходность также не назначается. При отсутствии
параметров комиссий/slippage запрещены net-метрики; при отсутствии versioned
политики после TP1 запрещена итоговая доходность такого остатка.

Каждая агрегированная цифра должна иметь ссылку на список `case_id`, определение
знаменателя, версию конфигурации и dataset hash.

## 12. План реализации после утверждения

Эти этапы описаны только как будущая работа и сейчас не выполняются:

1. **Dataset contract + validator.** Утвердить конечную дату и схему, получить
   данные от backend, реализовать manifest/validator и отчёт качества.
2. **Deterministic baseline.** Формализовать текущую стратегию `v0.0001` в
   versioned adapter без замены SMA-моделью; реализовать cutoff-safe features и
   детерминированную выборку.
3. **Execution engine + tests.** Реализовать entry/barrier state machines,
   консервативную ambiguity policy, формулы, property/unit/integration tests и
   фикстуры только после отдельного согласования реализации.
4. **Report + audit.** Реализовать immutable audit trail, ручную выборку 10 строк,
   отчётность и воспроизводимую сборку baseline-отчёта.
5. **LLM replay research.** Только после успешного baseline добавить отдельный
   non-deterministic режим с полными historical snapshots и независимой
   маркировкой результатов.

Переход между этапами требует review артефактов предыдущего этапа. Никакой этап
не разрешает подключение к реальному брокеру или проверку на реальных деньгах без
отдельного ТЗ и согласования.

## 13. Решения, которые нужно утвердить до реализации

- точная конечная дата вместо буквального `01.06.206`;
- точные текущие правила стратегии `v0.0001` и максимальные lookback;
- условия отмены до entry и условия review для `NO_TRADE`;
- политика после TP1;
- commission/slippage configuration без неявных defaults;
- определение точки origin и source cutoff относительно сессии и completed bars;
- правила непрерывного USDRUBF и ролловеров;
- алгоритм PRNG, master seed и отдельный audit seed;
- правила расчёта missed move и границы применимого наблюдения `NO_TRADE`.

Пока первый вопрос не закрыт, количественный протокол остаётся заблокированным.
